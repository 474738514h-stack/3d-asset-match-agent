# 迭代优化记录

> 从想法到可运行系统，三个判断直接决定了产品能否落地、能否规模化。每一轮都先判断问题是否值得解决、该解决到什么程度，再定方案并推动实现。
>
> 这是 README「三个关键判断」的完整展开版。

---

## 判断 1 · 草图解析不准，用描述里的名词纠正

**问题**：多模态解析草图时关键词经常不理想——草图潦草、主体容易被认错；但用户在描述框里手写的名词是明确意图，比模型猜测更可信。

**我做的判断**：定一条规则——**当文字与图片冲突时，文字里的具体名词强制覆盖图片解析的名词**。

**推动落地 → 结果**：
从描述中提取具体名词（犀牛、机甲、运动鞋…）覆盖模型给出的主体词，再叠加**两级锚点过滤**：具体名词做强锚点精确匹配、泛类（动物/角色）做弱锚点兜底、停用词表滤掉「模型/物品」这类无意义主体。
结果：搜犀牛仅返回犀牛，不再混入发动机、狗屋；识别成库里没有的品类（如牦牛）时也能靠文字纠正或友好返回空结果。**一次错误推荐就会损害信任，相关性是底线。**

## 判断 2 · 降本：不牺牲效果，控制 token 成本

**问题**：多模态识别是每次调用都要付的成本，草图白边多、分辨率高，直接送模型很费 token；但「识别品类/风格/颜色/主体几个词」是**轻量的结构化提取任务**，不需要旗舰大模型。降本从图片和模型两头做。

**我做的判断**：图片侧做预处理压缩，模型侧选轻量视觉模型——把成本花在关键处，而不是一味压缩。

**推动落地 → 结果**：
- **图片侧**：裁白边 → 长边缩到 512–1024 → JPEG 压缩，体积 20KB→4KB（**−79%**），视觉 token 随之大幅下降，识别不降反稳。
- **模型侧建议**：这类任务用**轻量视觉模型**就够了——首选**通义千问 Qwen3.7-Flash**（图像理解、支持 JSON 结构化输出，输入约 ¥0.2/百万 token），或**智谱 GLM-4.1V / GLM-4.5V-Flash** 档（国产、中文识别强、价格同为厘级量级）。避开两类误选：① 旗舰推理模型（贵 10–50 倍，还会输出思维链污染结构化结果）；② 纯文本模型（如 DeepSeek 系列不支持视觉）。

按压缩后几百 token/图估算，**单次识别成本约万分之二元，1 元可跑数千次**。原型阶段用免密钥方案省去后端代理，规模化时再切换到按量计费的轻量模型 API。

## 判断 3 · 海量资产，该不该做成数据库？

**问题**：26 个资产用扣子知识库验证逻辑没问题，但真实业务是**几十万到上百万**个 3D 资产——文档型知识库撑不起海量、也不擅长结构化过滤。

**我做的判断**：不该二选一，而要**分层**——扣子知识库是验证期的选择，规模化要用「结构化数据库 + 向量检索 + 混合召回」。

**推动落地 → 结果**：
生产级方案分四层：
1. 结构化字段（品类/风格/价格/授权/面数/格式）进 PostgreSQL 等关系库，做精确过滤与分面；
2. 把「名称+标签+描述」拼成文本做 embedding，进向量索引（pgvector / Milvus / Elasticsearch）做语义召回；
3. 查询时**先按结构化条件硬过滤**（预算、仅可商用、指定品类）缩小候选，再**向量语义召回 + 关键词精确匹配（BM25）两路并行**，融合重排后交给确定性打分；
4. 主库存源数据（唯一真相），向量索引是可重建的派生副本。

规模路径：**几十万级用 PostgreSQL + pgvector 一套搞定**，百万级以上再上 Milvus / ES 独立向量库。**现在的 RAG + 零内嵌就是这套架构的最小验证版——换库无需改动打分逻辑。**
