# 技术方案：PM 视角的关键取舍

> 这份文档不堆技术细节，而是回答面试官最可能追问的三个问题：**为什么这样选、怎么保证能落地、风险在哪**。它记录的是产品决策，不是代码说明。

---

## 一、为什么走 RAG，而不是把资产写死在代码里？

**表面看**：只有 26 个资产，把它们作为数组内嵌进代码最简单，检索逻辑几行就写完。

**但我判断这是错的**，原因是产品要活下去必须解决两个问题：

1. **资产会变**：真实平台每天上新、下架、改价。内嵌在代码里的资产，每次变动都要改代码、重新发布——运营无法自助维护，产品会被工程排期卡死。
2. **规模会涨**：26 个是验证用的样本，真实业务是几十万到上百万。写代码四件事决定了架构上限，而知识库/数据库方案天然可扩。

**所以从第一天就定下约束**：资产作为数据放进扣子知识库，检索逻辑与数据解耦。在 demo 里也能验证这条链路——增减资产只改知识库，不动一行代码。

> 一句话：我用 26 个资产验证的是一套「能接 26 万个」的架构，而不是 26 个资产的检索脚本。

---

## 二、为什么打分用确定性规则，而不是让大模型自由发挥？

**看起来更"智能"的做法**：把候选资产和需求一起丢给大模型，让它输出推荐理由和排序。

**我没这么做**，因为评分这个环节有三个硬要求：

| 要求 | 大模型自由发挥 | 确定性规则打分 |
|---|---|---|
| **可复现** | 同样输入两次结果可能不同，无法解释 | 同样输入永远同样输出 |
| **可归因** | 理由似是而非，分数怎么来的一团糊涂 | 每个分数能拆到品类/风格/色彩/关键词 |
| **成本可控** | 每次对全量候选做推理，费用随资产数增长 | 纯计算，零 token 成本 |

**具体做法**：兼容性按 42% 品类 + 26% 风格 + 20% 色彩 + 12% 关键词加权，综合分 = 兼容 46% + 画质 30% + 价格 24%。大模型只负责前半段——把模糊需求理解成结构化关键词；后半段的过滤、打分、排序交给代码节点。**让模型做它擅长的理解，让规则做它擅长的一致性。**

> 一句话：评分是产品对用户的承诺，承诺必须稳定、可解释、可审计——这恰恰是自由生成最不擅长的。

## 三、三处落地风险，怎么提前识别并定约束

风险不是联调时才发现的问题，而是在设计阶段就想清楚、定好边界的东西：

**风险 1 · 数据不真实，评分失真**
平台未公开面数、贴图分辨率、PBR 等字段，若直接编造会误导采购决策。
→ 约束：这些信息统一标「估算」徽标，与真实数据（售价、分类、体积、格式、热度）在界面上区分，并在 README 与作品集里做诚实声明。

**风险 2 · 召回不相干资产，一次就毁信任**
草图识别容易把主体认错，若把全量资产都拿去打分，结果里会混入完全不相关的资产。
→ 约束：两级锚点过滤——文字里的具体名词强锚点精确匹配，泛类弱锚点兜底，停用词表滤掉无意义主体；识别成库里没有的品类时，友好返回空结果而不是硬凑。

**风险 3 · 成本随规模失控，或误选模型**
旗舰推理模型贵 10–50 倍且输出思维链污染结构化结果；纯文本模型（如 DeepSeek）根本不支持视觉输入——这两类误选会让方案走不通。
→ 约束：图片侧压缩 −79%，模型侧锁定轻量视觉模型（Qwen3.7-Flash / GLM-4V 档），单次识别约万分之二元。原型用免密钥方案，规模化切按量计费 API。

## 四、一体两面：为什么前端原型和工作流都要做

常被问："这两套是不是重复做了两遍？"

不是。它们验证的是同一套逻辑的两端：

- **前端原型**验证「用户看得懂、愿意用」——渐进披露、并排决策、草图压缩都是在这里落地的，可上手点、离线也能演示。
- **扣子工作流**验证「能接真实大库、能规模化上线」——资产零内嵌、可发布成 Bot / API。

两者共享「理解 → 检索 → 打分 → 结论」的设计。产品化时，前端改调工作流 API 即可对接——这不是两个割裂的 demo，而是一条链路在两端的验证。
